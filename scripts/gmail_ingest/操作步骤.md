# Gmail 邮箱导出入库 · 操作步骤（T29 预案）

> 适用：S 邮箱（Takeout 已做好：单个 zip ≈6 GB，**不用切开**）→ 之后 A 邮箱（12.46 GB，**必须切开**，Takeout 选 2 GB 或 4 GB 分卷）。两个邮箱都接不进 Arena 的 Gmail 连接器，Drive 只有 15 GB 且不可扩容，
> 所以走「Takeout 导出 → 放到 Drive（临时「知道链接者可查看」）→ GitHub Actions 运行器下载解析 → 入库 → 删 Drive 上的导出件」。
> **不需要再另存新的 workflow**：复用 T28 的 `Drive SmartByte ingest`，代理在 `scripts/drive_ingest/RUN` 里写 `JOB=gmail` 即可转交到本管线。

## Simon 要做的（每个邮箱一次）

1. **用该邮箱登录** <https://takeout.google.com/>（S 邮箱就用 S 登录）。
2. 「取消全选」→ 只勾选 **邮件（Mail）** → 点「包含所有邮件数据」可保持默认（全部邮件，含垃圾箱/已发送）→ 下一步。
3. 导出设置：
   - 传送方式：**通过电子邮件发送下载链接**（不要选「添加到 Drive」，那会占 S 自己的 Drive 空间且不在我们这边的 Drive 里）；
   - 频率：**导出一次**；
   - 文件类型：**.zip**；
   - 文件大小：**2 GB 或 4 GB**（切成几个 zip，上传 Drive 更稳；单个 6 GB 的 zip 也能处理——管线按 zip64 流式读，本地已用 4.67 GB 单卷验证过）。
   - 点「创建导出」。Google 需要几十分钟到 1–2 天生成，完成后发邮件通知（链接 7 天有效）。
4. 下载全部 zip，上传到我们的 Drive（任意位置，建议新建文件夹《Gmail S 导出》放在一起）。
   **先把 Drive 上已入库的《SmartByte》删掉并清空回收站**（回收站里的文件 30 天内仍占配额），否则 15 GB 放不下。
5. 回复我「S 导出已上传」即可（文件夹名或链接更好）。**之后的共享设置、触发、监控、改回私有都由代理做**；
   我核对覆盖率报告无误后会回复「入库完成，可以删」，那时再删 Drive 上的导出件。

### A 邮箱（12.46 GB）放不下怎么办 —— 分批上传

Drive 删掉 S 导出件并清空回收站后，空余若 **≥ 12.5 GB** → 一次全部上传，按上面流程走；
若 **不够**（看 <https://drive.google.com/settings/storage>）→ **分两批**：

1. 先上传前一半分卷（如 `-001` ~ `-003`），回复我「A 第 1 批已上传，共 N 批」；
2. 我跑第 1 批（RUN 里加 `MORE_BATCHES=1`），完成后回复「第 1 批入库完成，可以删」；
3. 你删掉第 1 批、清空回收站，上传后一半分卷，回复「A 第 2 批已上传」；
4. 我跑第 2 批（不加 `MORE_BATCHES`），完成后核对总覆盖率，回复「A 全部入库完成，可以删」。

管线对分批的处理：Takeout 的分卷是按字节硬切的，一封邮件可能跨在两批之间；第 1 批末尾那半封会存成 `data/gmail_a/state/carry.bin`，第 2 批开跑时自动接在最前面，
**不丢、不重**。要全文保留的线程集合（`state/thr_keep.txt`）、本邮箱地址、Release 标签都跨批次沿用；`manifest.json` 里 `batches[]` 记录每批的文件、偏移、封数、完成状态，`status` 在最后一批前为 `awaiting_next_batch`。
分卷**必须按 Takeout 原顺序分批**（`-001` 在前），每批内部由管线按文件名自然排序。

> 为什么选 .zip 不选 .tgz：zip 可以不解压直接流式读里面的 .mbox；tgz 也支持，但要先解包。

## 代理要做的

1. `list_files` 找到导出件 → `make_public(file_id, role=reader, allow_file_discovery=false)`（每个 zip 都要设，或对文件夹设一次）。
2. 在 `scripts/drive_ingest/RUN` 写入并推送：

   ```
   JOB=gmail
   ACCOUNT=s
   SOURCE_IDS=<zip1 的 Drive ID>,<zip2 的 Drive ID>,...
   # 可选：OWN_EMAILS=s.sagatelecom@gmail.com   BULK_MODE=headers   OCR=0   LIMIT=0   FORCE=0
   # 分批上传时：非最后一批加 MORE_BATCHES=1（见上文「A 邮箱放不下怎么办」）
   ```

   推送即触发 workflow（与 Drive 任务共用并发组，排队不冲突）。
3. 监控分支上的 `drive-ingest[bot]` 提交：`data/gmail_s/_coverage.md`、`manifest.json`（`status: done`）。
   若 350 min 内没跑完，脚本会在 330 min 时优雅停止并提交（`status: partial`），再推一次 RUN 即从断点续跑（按字节偏移，不重复）。
4. 跑完：核对 `_coverage.md`（解析失败 0、附件失败可解释、原件备份 ✅）→ `make_private` 改回 → 回复 Simon「入库完成，可以删」。
5. 再跑 A 邮箱时把 `ACCOUNT=a`，其余相同（输出到 `data/gmail_a/`，Release `gmail-a-日期`）。
   分批时每批把 `SOURCE_IDS` 换成该批 zip 的 ID；非最后一批加 `MORE_BATCHES=1`；同一批续跑（partial）时 `SOURCE_IDS` 不变即可（按文件集合识别批次）。
6. **要再跑 Drive 任务时，先把 RUN 里的 `JOB=gmail` 行删掉或注释掉**，否则会转交到 Gmail 管线。

## 产出（`data/gmail_<账号>/`）

| 文件 | 内容 |
|---|---|
| `messages/<年>/<年-月>[_NN].jsonl` | 每行一封：收发人、主题、时间、Gmail 标签、线程 ID、方向、正文（群发/通知只留 600 字摘要）、附件清单、关联客户编号 |
| `attachments/text/<sha16>.json` + `attachments/index.json` | 附件正文（Word 表格 / Excel 逐行 / PDF 逐页 / PPT），按内容去重 |
| `threads.json` | 线程索引：主题、起止、封数、参与者、对方域名、客户编号 |
| `contacts.csv` | 每个对方地址：姓名、域名、收/发封数、首末日期、最近主题、Saga Clients 编号与等级 |
| `clients_link.json` | 按 Saga Clients 编号汇总往来（供回填 `Saga Clients/` 档案的跟进状态） |
| `_coverage.md` | 覆盖率报告：按年 / 方向 / 群发 / 标签 / 对方域名 / 附件类型 / 失败清单 / 备份 |
| Release `gmail-<账号>-日期` | Takeout 原件（≤1.8 GB 分卷 `.partNN`，按序 `cat` 还原） |
